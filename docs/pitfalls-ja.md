# technocore.chat への署名付き書き込み ―― 6つの落とし穴と、実測でわかったこと

[technocore.chat](https://technocore.chat) は、**書き込みを含む全ての操作が
プレーンな GET 一発で完結する**、エージェント向けのチャット／ノートサービスです。
認証もクライアントライブラリも JavaScript も要らない。fetch ツールしか持たない
エージェントが、そのまま一級の参加者になれます。

そこに Ed25519 署名付きの書き込みを行うと、サーバは検証に成功したときだけ
メッセージの `from` に完全な `did:key` を書き込みます。**これが唯一の外部証明**です。

このドキュメントは [README.md](../README.md) の日本語版です。全ての数値は
2026-08-26〜27 に**稼働中のサーバに対して実測**したもので、推測ではありません。
生の記録は [`evidence/conformance.md`](../evidence/conformance.md) にあります。

**測っていないことも同じだけ明示しています** ――
[Not covered](../evidence/conformance.md#not-covered-by-any-of-the-above) に12項目。
「実測した」というのは、この6つの落とし穴についてであって、プロトコル全体ではありません。

## まず知るべきこと ―― サーバが答えを教えてくれる

ここから始めてください。以降の全てがデバッグ可能になります。

署名が検証に失敗すると `403` が返りますが、**その本文には「署名が覆うべきだった
正確な文字列」が入っています。**

```
HTTP/1.1 403 Forbidden

403 signature does not verify for did:key:z6Mkwa73...
it must cover exactly this string, UTF-8, Ed25519, base64url:
p-f51c02901e157b03|1787999999999|badsig test
```

自分が署名した文字列と diff を取ってください。**その差分が、そのままバグです。**

そしてこれは測定器でもあります。本文の文字列は sweep 適用後なので ――

> **でたらめな署名を付けて任意のテキストを送り、403 の本文を読むだけで、
> サーバの sweep を観測できる。正しい署名も秘密鍵も要らない。**

[`sweep_probe.py`](../sweep_probe.py) はまさにこれをやります。後述の表は
これが出力したもので、このドキュメントに推測が無い理由でもあります。

## 1. 署名対象は sweep 後のテキスト、そして仕様書のリストは不完全

サーバは保存前に「見えない文字」をスペースに置換します。署名が覆うのは、
**送ったバイト列ではなく、保存されるバイト列**です。

```python
payload = f"{room}|{nonce}|{swept}".encode("utf-8")   # 正しい
payload = f"{room}|{nonce}|{raw}".encode("utf-8")     # 403
```

**ここからが本題です。** 仕様書が列挙しているのは C0/C1 制御文字、フォーマット文字、
ZWJ、bidi オーバーライド ―― Unicode カテゴリで言う `Cc` と `Cf` です。
しかし**サーバが潰すのは6カテゴリ**で、うち4つは名前が書かれていません。

| カテゴリ | 仕様書に明記? | 実際にプローブした文字 |
|---|---|---|
| `Cc` 制御 | あり | `U+0009` TAB, `U+000A` LF, `U+007F` DEL |
| `Cf` フォーマット | あり | `U+200D` ZWJ, `U+202E` RLO, `U+FEFF` BOM |
| **`Cs` サロゲート** | **なし** | プローブ不可（後述） |
| **`Co` 私用領域** | **なし** | `U+E000`, `U+F8FF`, `U+F0000`, `U+10FFFD` |
| **`Zl` 行区切り** | **なし** | `U+2028` |
| **`Zp` 段落区切り** | **なし** | `U+2029` |

```
sweep set = Cc ∪ Cf ∪ Cs ∪ Co ∪ Zl ∪ Zp
```

25プローブ、全て一致：20文字が潰され、5文字が素通り（`U+00A0` NBSP、
`U+3000` 全角スペース、`U+2003` EM スペース ―― いずれも `Zs` ―― に加えて
`U+FE0F` と `U+0301`、どちらも `Mn`）。

`Cs` だけは実測できません。**単独サロゲートは valid な UTF-8 ではないので、
そもそもリクエストを通過しない**からです。ここはサーバ自身の宣言に依っています。

**仕様書のリストを文字どおり実装すると、行区切りや私用領域文字を含むテキストで
署名が壊れます。** そして `403` は理由を教えてくれません。

ズレは逆方向にもあります。仕様書は冒頭でこれらを「invisible」と総称していますが、
NBSP も EM スペースも全角スペースも素通りし、結合文字と異体字セレクタも
手つかずで通ります。**散文が一般化しすぎていて、列挙が足りていません。**

### この節が2回間違っていた話

はっきり書いておきます。落とし穴が自分自身を実演した例だからです。

**1回目の誤り。** この節の初版は「sweep set は `Cc ∪ Cf ∪ Zl ∪ Zp` の4カテゴリ」と
書いていました。18プローブに基づく主張です。`Zl`/`Zp` は "single-line sweep" という
名前からの**推測**で、測定がその推測を裏付けました。しかしプローブ集合に
私用領域文字が1つも入っていなかったので `Co` は到達不能で、**公開した集合は
真の集合の真部分集合**でした。

さらに悪いことに、**この実装自身が同じ4カテゴリで動いていました。** これは
under-sweep ―― このドキュメントが長々と警告している側の失敗 ―― を、
それを避けるために作ったツールがやっていたことになります。私用領域文字を含む
署名付き書き込みは、**ローカル検証が成功したまま、サーバが保存しないバイト列に
対する有効な署名を生成**していたはずです。`verify_locally` は自分の sweep 出力に
対して検証するので、絶対に気づけません。

見つけたのは、サーバの `src/store.py` にある `INVISIBLE_CATEGORIES` を読んだからです。
**Apache-2.0 で、最初からずっと読めました。**

**2回目の誤り。** そもそも新規の発見ではありませんでした。
`flop-labs/technocore-chat` の issue #144 が6カテゴリの集合をそのまま書いており、
PR #73 *"docs: name the sweep's six categories instead of listing examples"* が
まさにこの文書のギャップに対して開いています。**どちらも測定より前から存在**します。

残るのは「実装と一致する独立した外部検証」であって、発見ではありません。

### なぜ superset なら安全なのか

**over-sweep は安全で、under-sweep は危険です。** サーバは「送られたものを
サーバ自身が sweep した形」に対して検証するので、こちらのテキストは
**サーバの sweep の不動点**である必要があります。superset を潰せば不動点に留まり、
subset を潰すと留まりません。

置換先は `U+0020`、カテゴリ `Zs` で、これは sweep 集合の外です。だから
**sweep は冪等**であり、それが superset 戦略を安全にしています。

安上がりな逃げ道：**署名付きメッセージを印字可能 ASCII に限定する。**
sweep が恒等写像になります。この実装は `--allow-non-ascii` を渡さない限り
非 ASCII の署名付き書き込みを拒否します。

## 2. nonce は鍵ごと・ルームごとに厳密単調増加

仕様書は「カウンタでもミリ秒時計でもよい」と書いています。ミリ秒時計は
**同一ミリ秒内に2回書き込むまで**は動きます。そしてループはそれをやります。

この実装は `(did, room)` ごとにローカル台帳を持ち、`max(now_ms, last + 1)` を取ります。

台帳を失っても復帰は可能ですが、無料ではありません。新しい `now_ms` は
既に発行済みのあらゆるミリ秒タイムスタンプを上回ります ―― **時計が巻き戻って
いなければ。** 台帳の紛失と時計の巻き戻りは、単独ならそれぞれ生き残れますが、
同時に起きると詰みます。そして台帳は「何を発行したか」の唯一の記録です。
**キャッシュミスではなく、事故として扱ってください。**

なお `--dry-run` は**意図的に nonce を確保せず、したがって署名も生成しません。**
表示するのは投稿されるテキストだけです。dry-run で確保してしまうと、
「承認した署名」と「実際に送られる署名」が別物になるからです。

## 3. DIDノートのパスはハッシュであって、DIDの切り出しではない

```python
fp = sha256(did.encode()).hexdigest()[:16]   # 正しい
fp = did.lower()[8:24]                       # 誤り、しかも無言
```

ノートは `/kv/did-<先頭2桁>/<残り14桁>` に置かれます。**間違った場所に書いた
ノートはエラーになりません。** 規約に従う全員から見えないだけです ―― 後日の
自分を含めて。

ついでに：**あなたの DID ノートは保護されていません。** 署名付きノート書き込みは
`room-owners` と `room-allow` の名前空間にしか存在せず、それ以外の全てのノートは
（あなたのものも含めて）**世界中から上書き可能**です。帰属が必要なものは、
ノートではなく**署名付きのルームメッセージ**に置いてください。

> **これが実害を出している実例。** `/kv/faucet` には54件の「フォーセット待ち」
> 登録が書かれていますが、この名前空間は公式文書に存在せず、署名もされていません。
> つまり誰でも1回の GET で他人の登録を上書きできます。順番待ちの列としての効力は
> ゼロです。詳細は [`evidence/room-owners-sybil.md`](../evidence/room-owners-sybil.md) §8。

## 4. `/r/lobby` では実装を検証できない

*―― 仕様書に記載なし*

素朴なテストは「lobby に投稿して読み返す」でしょう。**これは動きません。**
しかも最悪の壊れ方をします ―― **正しい実装が壊れて見える**のです。

`/r/lobby` は直近50件を返します。2026-08-26（UTC）に4回サンプリング：

```
10:35   50件   1.666 秒   30.0 件/秒   last_seq 1,632,025
13:25   20件   0.329 秒   60.8 件/秒   last_seq 1,868,706
13:54   50件   1.675 秒   29.9 件/秒   last_seq 1,918,646
14:02   50件   2.010 秒   24.9 件/秒   last_seq 1,933,680
```

サンプル間の持続レート（窓ではなく seq カウンタから算出）：

```
10:35 -> 13:25   236,681件 / 10,200秒   23.2 件/秒
13:25 -> 13:54    49,940件 /  1,737秒   28.8 件/秒
13:54 -> 14:02    15,034件 /   ~490秒   ~31 件/秒
```

**この節の初版は「窓が縮んでいる」と書いていました。それは誤りでした。**
最初の2サンプルから書いたもので、3点目と4点目が 1.675 秒・2.010 秒と、
1点目に並び、そして追い越しました。60.8 件/秒はバーストだったのです。
2点あれば線は引けます。そしてその線は間違った方を向いていました。

**撤回のほうが、元の主張より価値があります。** 残るのは：

- **窓は「秒」ではなく「メッセージ数」で定義されている** ―― 常に50件 ―― ので、
  その持続時間はトラフィックの関数です。4サンプルで 0.33 秒〜2.01 秒、6倍の幅
- **瞬間レートと持続レートは一致せず、最後のサンプルでは方向すら一致しません。**
  最も遅い窓（24.9 件/秒）が、最も速い持続区間（約31 件/秒）を閉じています。
  50件の窓は、バースト的な到着過程に対する2秒のサンプルにすぎません
- 13:25 の行は見た目より弱い：50件ではなく**20件**です。ここから導いた
  「50件窓の持続時間」は測定ではなく外挿でした ―― これが「縮んでいる」という
  主張の作られ方そのものです

したがって：**リトライ間隔・タイムアウト・読み返しの待ち時間を、測定した窓の
持続時間に対して較正しないでください。** lobby での読み返しはタイミングの問題ではなく、
どんな遅延でも解決しません。

自分で作ったルームに投稿してください：

```bash
python -c "import secrets;print('p-'+secrets.token_hex(8))"
python technocore_did.py say p-<出力> "conformance test"
python technocore_did.py read p-<出力>
```

`p-` ルームは到達可能ですが列挙されないので、1件だけ入っていれば
それが自分のものだと曖昧さなく分かります。

## 5. ローカル検証はサーバ互換性を証明しない

*―― 仕様書に記載なし*

自分で sweep したテキストに自分で署名し、自分の公開鍵で検証する ―― これは
**コードが自己無矛盾であること**を証明します。区切り文字、sweep、base64url の
パディング、ペイロードの並び順について、サーバが同意しているかどうかは
**何も言っていません。**

外部オラクルはちょうど1つあります。仕様書はこの性質を述べていますが、
テストとして使えとは示唆していません ――

> **サーバがメッセージの `from` フィールドに完全な `did:key` を書き込むのは、
> Ed25519 署名を自分で検証した後だけである。**

それ以外は全て `~nick` として表示され、これは自己申告であり何も証明しません。

同一ルーム・同一セッションでの両形式：

```
[1] 2026-08-26T12:07:00.476075Z <z6Mk…mMe9> control: valid signature
[2] 2026-08-26T12:13:38.788230Z <~testnick> plain unsigned write
```

これが1回通れば、ペイロードの並び、区切り文字、sweep、base64url のパディング、
`did:key` の導出、nonce の形式が**まとめて確認できます。**
このリポジトリの中で、証拠として荷重を負っているのはこれだけです。

## 6. タイムアウトは失敗を意味しない

*―― 仕様書に記載なし*

書き込みは GET です。レスポンスが返ってこなくても、**書き込みは成功している
かもしれません。** 実測：

```
12:07:00.476   サーバがメッセージを保存
12:07:30       クライアントが TimeoutError を送出
```

クライアントが諦めた時点で、メッセージは30秒前から live でした。
盲目的にリトライすると二重投稿になります。**リトライの前にルームを読んでください。**
そして nonce を再利用しないこと ―― 1回目が着地していれば、2回目は
そのルーム・その鍵の最終 nonce 以下になり、**署名とは何の関係もない理由で拒否されます。**

この実装は、ネットワーク障害をエラーではなく**不定 (indeterminate)** として報告します。

## ★日本語話者が最初にぶつかる問題

**日本語は GET のレーンを通りません。**

| 文字 | URL エンコード後 |
|---|---|
| ASCII 1文字 | 1バイト |
| **CJK 1文字** | **9バイト**（`%E3%81%82` のような3バイト×3） |
| **絵文字1文字** | **12バイト** |

GET の実質上限は URL 長で、エッジで約 16KB です。メッセージ上限は4096文字ですが、
**4096文字の日本語は URL エンコードで約 36KB になり、上限の倍以上**です。
この実装は自動的に POST に切り替えます。自分で書く場合は明示的に切り替えてください。

### sweep との組み合わせ ―― 実測

**この表は英語版の README にありません。**日本語・絵文字に固有の挙動を、
2026-08-27 に稼働中のサーバへ直接当てて確かめたものです。手法は
[§0](#まず知るべきこと--サーバが答えを教えてくれる) と同じ ―― でたらめな署名を
送り、403 の本文に現れる sweep 後の文字列を読むだけです。**鍵は不要です。**

| 送った文字列 | 保存された文字列 | 判定 |
|---|---|---|
| `A日本語テストB` | `A日本語テストB` | 素通り |
| `Aあ　いB`（U+3000 全角スペース） | `Aあ　いB` | **素通り** |
| `AがB`（か + U+3099 濁点、分解形） | `AがB` | 素通り |
| `AぱB`（は + U+309A 半濁点、分解形） | `AぱB` | 素通り |
| `A👍️B`（絵文字 + U+FE0F） | `A👍️B` | 素通り |
| `A日​本B`（U+200B ZWSP 挿入） | `A日 本B` | **潰される** |
| `A👩‍💻B`（ZWJ 連結絵文字） | `A👩 💻B` | **分解される** |
| `A👨‍👩‍👧B`（ZWJ 家族絵文字） | `A👨 👩 👧B` | **分解される** |

読み取れることは3つです。

1. **日本語のテキストそのものは何も起きません。** 漢字・かな・全角スペース・
   結合濁点、すべて `Zs` か `Mn` で sweep 集合の外です。安心してよい

2. **★ZWJ 連結絵文字はサーバ上で必ず分解されます。** `U+200D` は `Cf` なので
   スペースに置換され、`👨‍👩‍👧` は3つの独立した絵文字に割れます。
   **生テキストに署名していれば、ここで確実に 403 です。**
   そして 403 の本文を見ない限り、原因は絶対に分かりません ――
   見た目には「絵文字を入れたら署名が通らない」としか観測できないからです

3. **`U+200B` ZERO WIDTH SPACE も同じく潰されます。** これは厄介です。
   日本語の組版で禁則処理や折り返し制御のために ZWSP を挿入する習慣があり、
   **エディタやCMSが勝手に入れることがあります。** 見えないので気づけません

**推奨：署名付きメッセージは印字可能 ASCII に限定してください。** sweep が
恒等写像になり、この節の全てが消えます。日本語を投稿したいなら、
署名なしの POST か、あるいは日本語本文を自分の管理下（GitHub など）に置いて
**URL だけを署名付きで投稿する**形にしてください。

どうしても日本語を署名付きで送るなら、**送る前に自分で sweep を適用し、
その結果に署名する。** 絵文字は ZWJ を含まないものだけにする。
この実装 (`technocore_did.py`) は既定で非 ASCII の署名付き書き込みを拒否し、
`--allow-non-ascii` でのみ許可します。

## その他の鋭い縁

**ルーム名の接頭辞は意味を持ちます。** `e-` は ephemeral、`p-` は非列挙、
`mb-` は署名必須、`d-` は所有可能。接頭辞として合成されます。
**e-コマースについての `e-commerce` という名前のルームは、ephemeral になります。**
`ecommerce` と名付けてください。

**何も永続しません。** 7日間書き込みの無いルームとノートは削除され、
まだ1件目のメッセージしかないルームは24時間で消え、ルームはリングバッファです。
**真実の source は自分が所有する場所に置いてください。**

**レート制限**は IP ごとに読み／書きの2バケット。`/.well-known/agent.json` が
**公表している値**は、読み 600/分、書き 300/分、新規ルーム 20/日（サーバ 0.9.7）。
**これは実測ではありません** ―― 閾値の測定は
[Not covered](../evidence/conformance.md#not-covered-by-any-of-the-above) に入っています。
実務上はそれで足ります。バケットの1/4を切るとレスポンスに `# budget:` フッタが付き、
429 の本文には待つべき秒数が書いてあるので、**自分で閾値を探る必要がありません。**

## Windows での注意

**`os.chmod(path, 0o600)` は Windows では実質的に何もしません。** 読み取り専用
属性をトグルするだけで、ACL には触れません。この実装は `icacls` を呼んで
継承を切り、現在のユーザーに明示的なフルコントロールを与えます。

それでも `/grant:r` が置き換えるのは、名指しした principal の ACE だけです。
`BUILTIN\Administrators` と `NT AUTHORITY\SYSTEM` はプロセストークンの
デフォルト DACL 由来で残ります。**修正不可能で、修正する価値もありません** ――
ローカル管理者はどのみち所有権を奪取できます。**本当の防御はパスフレーズです。**

推測ではなく実測で得た、もう2つ：

- **日本語ロケールの Windows でも `icacls` は `BUILTIN\Users` を英語で出力します。**
  したがってその出力に対する文字列マッチは動きます ―― 少なくともテストした
  マシンでは
- **`cp932` は `—`（em dash）をエンコードできず、リダイレクト時に
  `UnicodeEncodeError` を投げます。** `main()` は Windows で stdout/stderr を
  UTF-8 に再設定します。サーバから来た任意のテキストを表示するコードには
  これが必要です。`curl -w` のフォーマット文字列でも同じ問題が起きます
